現在架構

1. 玩家輸入

Overlay Chat

文字、語音、截圖問題都先進後端；UI 顯示路徑泡泡讓玩家知道是否走本地或網路。

2. 地端路由

Qwen Intent Router

llama.cpp Vulkan / iGPU。判斷是攻略查詢、UI 指令、一般聊天、截圖 HUD，或 Hermes web。

3. 本地檢索

SQLite FTS5 + RAG Lite

用中文 n-gram、metadata、chunk index、相關片段與 evaluator 排序。

4. 回答決策

Direct / Summarize / Miss

高信心直接本地提示；需要整理則交給模型濃縮；不足才進 Hermes/Tavily。

5. 穩定保存

SQLite + Markdown

只保存濃縮後玩家可用提示；raw web result 和來源清單不進本地庫。

資料層

gamepath.sqlite 是搜尋主入口；gamepath/notes 是人類可讀攻略筆記。

模型層

地端 Qwen 做路由與候選評估；Hermes 做主回答、複雜推理與 Tavily web search。

演算法層

FTS5 先召回，RAG Lite chunk 取片段，metadata / core overlap / area overlap 做排序與 tie-break。

RAG Lite 怎麼達到

GamePath 的 RAG Lite 流程

  • 1. 寫入時先切資料：攻略濃縮成 Markdown，同步建立 gamepath_entries 與 gamepath_chunks。
  • 2. SQLite FTS5 建索引：entry 與 chunk 都進 FTS5；中文查詢用 n-gram / search terms 擴展，避免只靠完整詞。
  • 3. Query 先由 Qwen gate：地端 Qwen 判斷是不是攻略問題；不是攻略就不查 GamePath，避免負例誤命中。
  • 4. 本地召回候選：用玩家原始問句查 SQLite FTS5，找出 entry 與 chunk 片段。
  • 5. 輕量 rerank：用 core overlap、match coverage、metadata、area/entity/tags、trust state 重新排序。
  • 6. 決定回答路徑：高信心 direct；中信心 summarize；低信心 miss 後交給 Hermes/Tavily。

一句話定義

GamePath RAG Lite 是「不用 embedding model 的本地 RAG」： 它用 SQLite FTS5 做召回，用攻略 metadata 與 chunk evaluator 做排序， 再把命中的片段交給 Qwen/Hermes 濃縮成玩家可讀提示。

它的目標不是做最強語意搜尋，而是在 iGPU / RAM 有限環境下， 用很低資源成本做到「夠快、可控、可重建」的攻略查找。

和傳統 RAG / GraphRAG 的差異

架構 怎麼找資料 需要模型/索引 優勢 限制 GamePath 關係
GamePath RAG Lite SQLite FTS5 + 中文 n-gram + chunk index + metadata rerank 不需要 embedding model；只用既有 Qwen 做 gate/摘要 輕量、可離線、容易打包、iGPU 壓力低 同義詞很遠、完全不同說法時不如向量檢索 目前採用
傳統 Vector RAG 把文件切 chunk，轉 embedding，向量相似度召回，再交給 LLM 回答 需要 embedding model、vector DB 或向量索引 語意改寫能力更好，適合大量自然語言文件 多一個模型和索引；RAM/磁碟/打包複雜度上升 未來資料量變大可選配
GraphRAG 抽取實體、關係、事件，建立圖，再用圖社群/路徑找上下文 需要 entity extraction、graph store、graph retrieval、摘要維護 擅長跨章節、角色關係、事件因果、世界觀整理 建置成本高；小型攻略查詢會顯得太重 不是目前架構

是不是 GraphRAG？

不是。現在 GamePath 沒有建立「角色 A 在地點 B 遇到敵人 C」這種節點與邊， 也沒有做 graph community summary 或 graph traversal。它比較接近 lexical / hybrid 的輕量 RAG。

但它有 GraphRAG 的前置條件：entry 內已經有 game_id、area、entity_type、entity_name、tags、trust_state。 未來要升級 LLM-wiki 或 GraphRAG，可以從這些 metadata 產生節點與關係。

為什麼現在不用完整 RAG

目前你的重點是遊戲中即時體驗：不能讓 iGPU 同時背太多模型，也不能讓安裝包變複雜。 所以先用 SQLite FTS5 承擔查詢，Qwen 只做意圖 gate 和必要摘要，是比較穩的折衷。

等 GamePath 變成大型 LLM-wiki 後，再補 embedding reranker 或 GraphRAG 會比較合理； 那時 GraphRAG 可以用在角色、地點、任務、道具用途的跨文件推理，而不是每次小查詢都啟動。

玩家使用流程

  • 問攻略：「二樓聽到歌聲是哪隻怪？」
  • Qwen 分流：判定為 gamepath_query，產生 query、tags、spoiler level。
  • GamePath 搜尋：查 SQLite FTS5 與 chunk index，抓到最相關片段。
  • 本地回覆：命中 #143「唱歌女殭屍」後，整理成 Hint 1/2/3。
  • 不足才查網路：GamePath miss 或最新版/patch 問題才進 Hermes/Tavily。
  • 可重用才保存：Hermes 查到的攻略被濃縮後寫入 GamePath，下次類似問法直接命中。

UI 狀態泡泡代表什麼

gamepath_hit 本地已命中，可以快速回答。

gamepath_summarizing 本地有資料，但需要模型濃縮。

gamepath_miss 本地不足，可能交給 Hermes/Tavily。

gamepath_stored 濃縮提示已寫入本地庫。

general_chat / ui_command Qwen 判定不是攻略，不查 SQLite。

為什麼這樣設計

優勢

  • 快：本地命中時不需要 Tavily，也不用重新查網路。
  • 省：SQLite + FTS5 不需要額外 embedding model，適合 iGPU / RAM 有限環境。
  • 穩：可重用攻略被保存成 Markdown + SQLite，後端迭代不會洗掉知識。
  • 可控：Qwen 只做路由和評估，不直接執行 UI 或系統動作。
  • 低劇透：先回 Hint ladder；玩家要求完整答案時才升高劇透層級。

劣勢 / 風險

  • 不是完整語意向量：完全不同說法、沒有共通詞時，仍可能需要 Qwen evaluator 或未來 reranker。
  • 不能無腦每句都查：hard negative 顯示純 SQLite 會有誤命中，正式流程必須保留 Qwen intent gate。
  • 總延遲不只 SQLite：玩家感受到的等待還包含 Qwen 意圖判斷、Qwen/Hermes 摘要。
  • 大型 wiki 需要治理：超過 10k 筆或長篇攻略包需要快取、分區索引、去重與版本策略。

測試結論

本輪使用 30 筆攻略正例與 8 筆非攻略負例，全部來自正式 GamePath 使用情境。Qwen 最適合放在「要不要查 GamePath」這一層，能擋掉一般聊天、UI 指令、玩家記憶、HUD 標記、最新版網路問題，避免 SQLite 硬湊答案。

但目前不建議讓 Qwen 改寫後的 query/tags 取代玩家原句作為主檢索，因為真實資料測到 Top-1 會從 100% 降到 80%。穩定做法是：玩家原句主查，Qwen query 只作輔助或 debug。

未來與 LLM-wiki 的整合

1. Markdown 當原始知識

gamepath/notes/{game_id} 可直接成為 LLM-wiki 頁面來源。人可以讀，模型也可以重建索引。

2. SQLite 當查詢索引

SQLite 保存 entry metadata、FTS5、chunk FTS。未來 wiki 重整時可以刪掉重建，不破壞 Markdown 本體。

3. 版本與可信度治理

加入 game version、來源品質、verified / disputed 狀態，讓舊攻略不會污染新版路線。

推薦演進路線

  • 短期：加 Qwen intent / hint summary TTL cache，先改善玩家體感延遲。
  • 中期：LLM-wiki 目錄化，按 game_id、area、entity_type 產生頁面。
  • 長期：可選 semantic reranker 或 embedding adapter，只在大型 wiki / 難 query 啟用。

整合後資料流

Web search 或玩家保存 → Hermes/Qwen 濃縮 → Markdown wiki page → SQLite chunk index → GamePath 搜尋 → Hint ladder 回覆。

這樣能讓攻略知識穩定累積，又不把 raw web search 或整篇攻略直接塞給玩家。

一句話結論： GamePath 現在足以支撐數千筆本地攻略的快速精準查找；但它應該被 Qwen intent router 保護， 只處理攻略型問題。未來接 LLM-wiki 時，Markdown 當知識本體、SQLite/RAG Lite 當可重建索引，是最穩的方向。
